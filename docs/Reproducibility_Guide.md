# Reproducibility Guide

How to reproduce the A-DMFE platform, its experiments, and every numbered
result artifact shipped with this repository. Paths below are relative to the
repository root.

## 1. Environment

Verified on Windows 11 with:

- Python 3.14.5 (virtualenv at `backend/.venv`)
- Node.js v24.12.0, npm 11.6.2
- OR-Tools 9.15.6755 (SWIG bindings; emits benign DeprecationWarnings on import)

Python dependencies are pinned in `backend/requirements.txt`.
Key packages: FastAPI 0.139.2, Uvicorn 0.51.0, SQLAlchemy 2.0.51,
Pydantic 2.13.4 + pydantic-settings 2.14.2, pytest 9.1.1, httpx 0.28.1.

## 2. Backend setup

```
python -m venv backend/.venv
backend/.venv/Scripts/python -m pip install -r backend/requirements.txt
```

The backend boots without a `.env` (a dev SECRET_KEY fallback is used with a
startup warning, see `backend/app/core/config.py`). Optional configuration:

- `SECRET_KEY` - set in `backend/.env` for anything non-development.
- `DATABASE_URL` - default is SQLite `dmfe_dev.db`, created relative to the
  current working directory; start the server from `backend/` to keep a single
  database file.
- `GOOGLE_MAPS_API_KEY` - optional; haversine fallbacks are used when absent.

Start the API from `backend/`:

```
backend/.venv/Scripts/uvicorn app.main:app --reload --port 8000
```

## 3. Frontend setup

From `frontend/`:

```
npm install
npm run dev
```

Dev UI: http://localhost:5173 (allowed origin by default).

## 4. Test suite

From `backend/`:

```
.venv/Scripts/python -m pytest tests/ -q
```

Current status: 59 tests, 0 failures.

## 5. Experiment pipeline

All experiment scripts live in `backend/evaluation/` and must be run from that
directory with `..\.venv\Scripts\python -m <script>`.

Determinism scheme (single-pass simulated workloads; no ML stochasticity):

- Canonical seed = `1000 + workload` (e.g. 1050 for workload 50).
- Repetition seed = `1000 + workload + i*97`, i = 0..4.
- Workloads: `[50, 100, 250, 500]`.

Pipeline order (each step reads the previous step's cache if present; see
`framework.py` `load_or_run(..., force=True)` to force recomputation):

| # | Command (from `backend/evaluation/`) | Writes to `evaluation/results/` |
|---|--------------------------------------|--------------------------------|
| 1 | `run_admfe_experiments` | `admfe_{static,adaptive}_experiments.json`, `admfe_repetitions.json`, `admfe_learning_ab.json`, `research_summary.md`, comparison/per-workload CSVs |
| 2 | `final_validation` | `final_metrics_table.md`, `final_statistical_summary.csv`, `final_improvement_summary.md` |
| 3 | `phase8_validation` | `learning_validation.md`, `xai_validation.md` |
| 4 | `make_admfe_report` | `performance_profile.md`, `ieee_tables.md`, `ieee_tables.tex`, `graphs/*.json` |

Expect several minutes per workload pair at volume 500 (batch-formation is the
dominant cost; see `performance_profile.md`).

## 6. Result artifacts

All generated results are under `backend/evaluation/results/` and are fully
regenerable (the seed scheme above is deterministic). `.db` and `.log` files
are runtime-generated and git-ignored.

## 7. Honesty notes baked into the artifacts

- Graph JSON files under `results/graphs/` feed the static dashboard; they are
  regenerated by `make_admfe_report`.
- The live-tracking map shows driver positions from seeded sim state polled
  over REST (`/vehicles/locations`). It is not GPS and is not real-time push
  (no WebSocket) - treat it as a visualization of simulator state.
- Repeated-seed results are descriptive (mean/std/min/max over RNG variation),
  not statistical significance tests.
